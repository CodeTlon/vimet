## Identidad del Proyecto
- **Cliente:** VIMET — Vida y Metabolismo (Avril Jerushalmi + Gerónimo Gallardo)
- **Tipo:** L3 — Web app con auth + booking + dashboard admin (migración desde stack PHP MVC + MySQL)
- **Generado:** 2026-05-09
- **URL Producción:** pendiente
- **Repo GitHub:** CodeTlon/vimet
- **Deploy:** Vercel (auto-deploy on push a `main`). Supabase aparte.

## Origen del proyecto
Migración desde sitio PHP MVC propio (en `client-assets/vimet/vimet/`) que corría sobre Laragon + MySQL. Ver `docs/migration-report.md` para mapeo legacy → nuevo stack.

## Stack
- Next.js 14 (App Router), TypeScript, Tailwind CSS, Shadcn/UI, Lucide React
- Supabase: sí — tablas: `profiles`, `servicios`, `horarios_disponibles`, `turnos`, `bloqueos_horario`, `fichas_paciente`, `mediciones_antropometricas`, `evaluaciones_funcionales`, `planes`, `plan_secciones`, `plan_seccion_comidas`, `plan_seccion_imagenes`, `feedback_semanal`, `feedback_mensajes`, `evolucion_entradas`, `objetivos`, `recursos_paciente`, `contenido_sitio`. Bucket Storage: `planes` (privado, PDFs + imágenes de secciones) + `recursos` (privado, multimedia + adjuntos de feedback) + `sitio` (público, fotos de perfil + contenido).
- Resend: sí — solo formulario de contacto público (sin almacenamiento en DB)
- Fuentes: Outfit (headings) + DM Sans (body) — vía `next/font`

## Identidad de Marca

- **Ciudad:** Córdoba, Argentina (Instituto VIANETT, Av. Pedro Simón Laplace 5573)

## Base de Datos (Supabase)
| Tabla | Campos relevantes | RLS |
|-------|-------------------|-----|
| `profiles` | id (=auth.users.id), nombre, apellido, telefono, rol, activo, `activado_en` (timestamptz, null hasta la primera activación — distingue "pendiente" de "inactivo" en `/admin/pacientes`), `gestionado_por_staff` (boolean, default false — paciente dado de alta por staff sin login propio, ver Quirks), `slot_publico` (text, `'avril'`\|`'gero'`\|null, único parcial — identifica qué cuenta ocupa cada tarjeta de "Perfil público", independiente del email, ver Quirks) | select propio + admin all |
| `servicios` | id, nombre, descripcion, duracion_minutos, tipo, icono, profesional_id | select público |
| `horarios_disponibles` | id, profesional_id, dia_semana, hora_inicio, hora_fin, modalidad | select público |
| `turnos` | id, paciente_id, profesional_id, servicio_id, fecha, hora_inicio, hora_fin, modalidad, estado, notas_paciente, notas_profesional, turno_par_id | paciente ve sus propios + profesional ve los suyos + admin all |
| `bloqueos_horario` | id, profesional_id, fecha_inicio, fecha_fin, motivo | select público |
| `fichas_paciente` | 1:1 con paciente — datos personales, hábitos, salud, lab, motivos | paciente lee la suya + staff todo |
| `mediciones_antropometricas` | histórico: peso, talla, IMC (calculado), %grasa, %músc, kg grasa/músc, dx, + datos ISAK opcionales (8 pliegues mm, 3 perímetros cm, `kg_tejido_muscular`/`kg_tejido_oseo`, migración `0034`) para IMO/Adiposidad/Muscularidad — ver Quirks | paciente lee + staff escribe |
| `evaluaciones_funcionales` | 8 tests (4×10 + 1×10 + 2×15 + 1×20 = 100) + `puntaje_total` generated | paciente lee + staff escribe |
| `planes` | tipo (nutri/entreno/combo), título, estado, fecha_desde/hasta, archivo_path, campos estructurados de nutrición (6 columnas fijas, "Pautas nutricionales") + entrenamiento (fijos, no modulares) | paciente lee los suyos + staff escribe |
| `plan_secciones` / `plan_seccion_comidas` / `plan_seccion_imagenes` | Secciones modulares de un plan que el profesional agrega a voluntad — tipo (`receta`/`comidas_dia`/`imagenes`; el enum de DB conserva un 4to valor `pautas_generales` sin uso, ver Quirks), título, contenido, `orden` (reordenable); `plan_seccion_comidas` son los momentos del día de una sección `comidas_dia`; `plan_seccion_imagenes` son imágenes en el bucket `planes` (ilustran receta, o son el contenido único de una sección `imagenes`) | paciente lee las de sus planes + staff escribe |
| `feedback_semanal` | unique(paciente,semana_inicio): estado físico, ánimo, energía, adherencias, peso. `dudas`/`respuesta_profesional`/`respondido_*` quedan legacy (el Q&A nuevo vive en `feedback_mensajes`) | paciente CRUD propio + staff lee/responde |
| `feedback_mensajes` | Chat de la semana: `feedback_id`, `autor_id`, `contenido`, `created_at`, `edited_at`. Solo se escribe mientras `feedback_semanal.semana_inicio` es la semana actual (chequeo en la Server Action, no en RLS); solo se edita el último mensaje propio | select/insert propio o staff (ownership vía `feedback_semanal`); update solo `autor_id = auth.uid()` |
| `evolucion_entradas` | timeline: origen, tipo, contenido, `visible_paciente` | staff CRUD + paciente lee solo las visibles |
| `objetivos` | categoría (5), descripción, estado (4), fecha_objetivo | paciente lee + staff escribe |
| `recursos_paciente` | tipo (link/pdf/imagen/video), categoria (5), titulo, descripcion, url, storage_path, `visible_paciente`, plan_id | staff CRUD + paciente lee solo los visibles |

**Roles** (campo `rol` en `profiles`): `paciente` (default), `nutricionista`, `entrenador`, `admin`. `admin` ya no es un nivel de permiso distinto para el contenido del sitio: desde la migración `0010` (servicios/ubicación/metodología) y `0032` (perfil público — foto/teléfono/bio de `profiles`, ver Quirks), cualquier staff (`nutricionista`/`entrenador`/`admin`, vía `is_staff()`) puede crear/editar servicios, ubicación, metodología y perfiles públicos de **cualquier** profesional, no solo el propio — `admin` sigue siendo el único que puede reasignar el `rol` de otro usuario (trigger de `0006`, sigue en `is_admin()`).
**Trigger:** `on_auth_user_created` → inserta fila en `profiles`. Rol por defecto `paciente`; si el usuario fue **invitado** (`auth.users.invited_at` no null) y trae `rol` válido en `user_metadata`, respeta ese rol (registro público siempre cae en `paciente`). El dashboard de Supabase no expone metadata al invitar → para staff, invitar y luego setear `rol` en `profiles` desde el Table/SQL editor.
**Storage bucket** `planes` (privado): paths `{paciente_id}/{filename}`. Staff todo, paciente solo lee su propia carpeta. Acceso vía signed URL (5 min TTL).
**Storage bucket** `recursos` (privado): paths `{paciente_id}/r/{ts}_{file}` (staff) y `{paciente_id}/f/{semana}_{ts}_{file}` (adjuntos de feedback, subidos por el paciente). Signed URLs con TTL 1 hora. Paciente puede insertar/borrar solo en subcarpeta `f/`; staff full access.
**`feedback_semanal.adjunto_path`**: columna opcional (text) para el archivo que el paciente adjunta a su feedback semanal. Se sube al bucket `recursos` desde `enviarFeedbackAction`. Al re-subir se borra el anterior del bucket antes de sobrescribir la columna.
**Storage bucket** `sitio` (público): paths `staff/{profileId}/{ts}.webp`. `actualizarPerfilPublicoAction` borra la foto de perfil anterior del bucket al reemplazarla (parsea el path desde la `foto_url` guardada).
**Optimización de imágenes**: toda foto que sube un usuario (foto de perfil, recursos tipo imagen, adjuntos de feedback que sean imagen) pasa por `optimizeImage()` (`lib/storage/optimize-image.ts`, `sharp`) antes de ir a Storage — resize a max 1600px + reencode a webp calidad 80. Video de recursos NO se transcodifica server-side (sin ffmpeg en el proyecto) — solo se bajó el tope de subida a 40MB.

## Quirks y Advertencias
- **Secciones modulares de un plan (migraciones `0037_plan_secciones.sql` + `0038_revertir_pautas_generales_seccion.sql`, `actions/plan-secciones.ts`).** El profesional agrega a un plan las secciones que necesite, de 3 tipos: `receta`, `comidas_dia` o `imagenes` (ver `TIPO_SECCION_PLAN`/`TIPO_SECCION_PLAN_LABEL` en `lib/seguimiento.ts`). **"Pautas nutricionales" (6 columnas de texto en `planes`: pautas_generales/pautas_hidratacion/pre_entreno/intra_entreno/post_entreno/suplementacion), "Datos de entrenamiento" y la rutina de ejercicios (`plan_ejercicios`) NO son parte de este sistema** — siguen siendo bloques fijos en `plan-form.tsx`/`planes`, decisión explícita confirmada con el usuario (la 0037 había intentado modularizar también "Pautas nutricionales" partiéndolo en 6 secciones sueltas — la 0038 revierte eso puntualmente: recompone las 6 columnas desde esas secciones y las vuelve a borrar; el enum `tipo_seccion_plan` de la DB conserva el 4to valor `pautas_generales` sin uso posible desde la app — no se quita del enum porque Postgres no permite remover valores de un enum sin recrear el tipo, y no hace falta: el zod de `crearSeccionAction`/`actualizarSeccionAction` y el picker de `TIPO_SECCION_PLAN` ya no lo ofrecen). Una sección `comidas_dia` tiene N "momentos del día" con nombre libre (`plan_seccion_comidas.nombre_momento` — no hay una lista fija de "Desayuno/Almuerzo/...", el profesional pone los que necesite, ej. "Media mañana en el trabajo"). Las secciones son **opcionales**: un plan se puede guardar sin ninguna (mismo criterio que ya existía para la rutina, que también se agrega recién después de guardar el plan porque necesita un `plan_id`). Reordenables con flechas subir/bajar (`moverSeccionAction`, swap de `orden` con la vecina). Imágenes van al bucket `planes` ya existente, path `{paciente_id}/secciones/{seccion_id}/...webp` (vía `optimizeImage()`, igual que el resto del sitio) — `receta` las muestra normal como ilustración, `imagenes` es una sección exclusivamente de imágenes pensada para una futura función de imprimir el plan y **a propósito se ve chica** en el detalle del paciente (tira de miniaturas, no grande). El componente compartido `<Modal>` (`components/ui/modal.tsx`) nunca desmonta a sus hijos (solo hace `showModal()`/`close()` sobre el `<dialog>`), así que `PlanSeccionesPanel` fuerza un remount de `PlanSeccionForm` con una `key` que suma 1 en cada apertura — sin esto, editar la sección A y después la B mostraría los momentos/valores de A pegados en el form de B. Ambas migraciones ya están aplicadas contra el Supabase de dev (a mano vía SQL Editor, sin credenciales de CLI/DB directo en el entorno, igual que otras migraciones anteriores). **Pendiente**: falta una pasada manual en el navegador (crear/editar/reordenar/eliminar una sección de `receta`/`comidas_dia`/`imagenes`, y confirmar que "Pautas nutricionales" volvió a verse como bloque único en `/mis-planes/[id]`) antes de confiar en la feature en producción.
- **Ejercicios de cardio (`ejercicios.modo`, migración `0031`):** un ejercicio del catálogo es `modo='fuerza'` (default) o `modo='cardio'` — es propiedad del ejercicio, no del plan ("Salir a correr" es cardio en cualquier plan donde se use). Un `plan_ejercicios` de un ejercicio `cardio` no usa `series`/`repeticiones`/`descanso_seg`; usa 3 pares valor+unidad (`cardio_entrada_calor_*`, `cardio_trabajo_principal_*`, `cardio_vuelta_calma_*`, unidad ∈ minutos/horas/km) — un constraint en la DB exige que cada par esté completo o vacío, nunca a medias (`guardarFaseCardio` en `rutina-panel.tsx` es la única función que escribe estos campos, y sabe mantener el par consistente; no escribirlos por otro lado sin replicar esa lógica). `rutina-panel.tsx` (staff) y `rutina-viewer.tsx` (paciente) muestran fuerza y cardio en **bloques separados** dentro del mismo día — no es una tabla mixta, por decisión explícita (las columnas Series/Reps/Descanso no tienen sentido para una fila de cardio). `resumenCardio()` en `lib/seguimiento.ts` arma el texto legible para el paciente.
